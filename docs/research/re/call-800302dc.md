# Block at 0x800302dc

This follows [call-800302d4.md](call-800302d4.md). The byte at offset `0x35` is positive. `slti` in that note's delay wrote `v0`. The byte is still in `v1`. `s0` is the object.

`beq v0, zero, 0x8003031c` is taken when the byte is 3 or more, because `slti` compared it with 3 and wrote 0. The delay `sll v0, v1, 5` still runs. [call-800302cc.md](call-800302cc.md) traces the epilogue at `0x8003031c`. It does not write the object.

When the byte is 1 or 2, `v0` is 1 and the branch is not taken. The same delay leaves `v0` as the byte shifted left by 5. `lui` and `addiu` make `0x8009f368`. `addu` adds the shifted byte, so `a0` is `0x8009f388` for byte 1 and `0x8009f3a8` for byte 2. `jal` at `0x800302f0` targets `0x80079b24`. The delay copies the object into `a1`. `ra` is `0x800302f8`. `python3 tools/sdk_match.py` does not name `0x80079b24`. This note does not enter that body.

## Our code

`components/exe/call_800302a4.cpp` returns when the byte is 3 or more. For 1 or 2 it calls `call_80079b24`. No ledger row is added.
