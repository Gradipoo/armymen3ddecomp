# Display fill at 0x80076274

Traced on the local USA executable. The function starts at `0x80076274`.
This boot arrives from [call-80076414.md](call-80076414.md) with a zero color
argument. The saved return address is `0x8007641c`.

The path is straight through to the return. It contains 38 instructions,
including delay slots. It has no unnamed calls and ends before the
64-instruction cap. The text range is 152 bytes. Ghidra's exported body
size agrees with that range. Ghidra's C and the instruction listing stay
under `build/`. The SDK bodies were not entered.

At `0x80076284`, the function calls `DrawSync`. The delay slot supplies
argument zero. The return address is `0x8007628c`. Its return value is
discarded. The name comes from the existing SDK matcher.

After the wait, the function builds a four-word packet on its stack. The
high byte of the tag is 3. The next word has command byte 2 and the low
24 bits of the color argument. The color's high byte is discarded. The
first three bytes of the tag are not initialized along this path.

The display state base is `0x800e15b0`. A pointer at offset `0x0c` supplies
the origin. Its halfwords at offsets 4 and 8 are the origin coordinates.
Halfwords at display offsets `0x1c`, `0x20`, `0x24`, and `0x28` supply left,
right, top, and bottom. The packet coordinates are origin plus left and
origin plus top. Its dimensions are right minus left and bottom minus top.
The stored results retain the low 16 bits. This note does not read or
quote the pointed-to origin values. The display state lies beyond the
loaded text image and is runtime state.

At `0x800762f4`, the function calls `DrawPrim` with a pointer to the packet
as `a0`. The delay slot finishes writing its vertical coordinate. The
return address is `0x800762fc`. Other argument registers are not treated
as interface arguments here. The name comes from the existing SDK matcher.
The return value is discarded. The function restores its saved registers
and returns through `ra` at `0x80076304`. Its delay slot releases the frame.
This boot next reaches `0x8007641c`. Those words are not traced here.

## Our implementation

`components/exe/display_fill.cpp` implements the packet arithmetic and call
order. The caller supplies a typed view of current display state and a GPU
interface. It does not cast a retail address to a host pointer. State is
read after the wait. Packet words use explicit bit positions, independent
of host byte order. Our interface initializes the unspecified low tag bits
to zero. Their retail value is not a claim of this implementation.

The C++ test checks call order, color masking, coordinates, dimensions,
16-bit wrap, and a state change during the wait. This is a host model.
It is not wired into the launcher or a GPU backend. The executable-load
gap stays open. The ledger status is implemented, not verified.

## First compiler experiment

Our separately written local C candidate used the semantics above. It was
compiled with the pinned GCC 2.7.2 PSX, maspsx in ASPSX 2.56 mode, and LLVM
23.1.5. The flags are recorded in `docs/TOOLCHAIN.md` and the local provenance.

The first assembly attempt used absolute symbolic globals. LLVM rejected
those memory macros in MIPS I mode. The second used an explicit state
address and resolved the two known call symbols with assembly constants.
It assembled without unresolved relocations. Its section was 168 bytes,
compared with the reference's 152 bytes. The comparison correctly rejected
the size mismatch. No bytes were trimmed or masked.

The candidate uses repeated global address loads and different scheduling.
Possible causes include source types, address-expression form, compiler
flags, and assembler behavior. This result does not establish which
compiler produced the game. No matching claim is made. Candidate C,
assembly, object code, and logs remain under `build/`.
