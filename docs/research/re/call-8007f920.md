# Call at 0x8007f920

Traced fact from the USA PS-X EXE. Re-check on a disc you own with `python3 tools/entry_disasm.py build/disc/SLUS_004.91 --start 0x8007f920`. The executable and the listing stay in `build/`.

The start address is `0x8007f920`. The `jal` at `0x8002525c` set `ra` to `0x80025264` and jumped here. That call is in [call-8002523c.md](call-8002523c.md). Both paths into that `jal` leave `a0` as `0x8009f820`, `a1` as 0, and `a2` as `0x9a4`. Which path this boot took is still unknown. The tool followed 1 instruction and stopped at the first branch. The hard cap is 64 instructions. This block ended before the cap.

`beq` at `0x8007f920` branches to `0x8007f9a0` when `a0` is 0. When `a0` is not 0, the branch is not taken. The delay slot at `0x8007f924` is `addu v0, a0, zero`, so `v0` becomes a copy of `a0` on both outcomes. Re-check it with `--start 0x8007f924`. That run's first instruction is the `addu`. The words after that instruction are not traced. The fall-through address is `0x8007f928`.

This call enters with `a0` equal to `0x8009f820`. That value is not 0, so the branch is not taken. The branch tests `a0`. The delay slot copies `a0` into `v0`, so `v0` leaves as `0x8009f820`. These two words do not read or write `a1` or `a2`. `a1` stays 0 and `a2` stays `0x9a4`. They do not write `ra` or `sp`, so `ra` stays `0x80025264` and the stack slots saved at `0x800251f8` stay as they were.

After the delay slot, this call continues at `0x8007f928`. The body at `0x8007f928` is not traced. The body at `0x8007f9a0` is not traced. The words at `0x80025264` are not traced. The caller return at `0x8007faec` is not traced. This note does not close the gap in `components/exe/load.cpp`.
