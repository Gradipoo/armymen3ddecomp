# Block at 0x80010cc4

Traced fact from the USA PS-X EXE. Re-check on a disc you own with `python3 tools/entry_disasm.py build/disc/SLUS_004.91 --start 0x80010cc4`. The executable and the listing stay in `build/`. That tool stops at the first jump, the `jal` at `0x80010cc8`. Re-check the delay slot with `--start 0x80010ccc`. That run's first instruction is the `addu`. The words after that instruction are not traced.

The start address is `0x80010cc4`. This is the rest of the function that started at `0x80010c90`. It is the return from the `jal` at `0x80010cbc`, and it is also the branch target when the word at offset `0x74` is zero. See [call-80010c90.md](call-80010c90.md) and [call-8001b298.md](call-8001b298.md). `s0` is the object. `s1` is the incoming second argument. The word `0x800be768` is already stored at offset `0x68`. The frame is still open. The slot at `0x10(sp)` holds the old `s0`. The slot at `0x14(sp)` holds the old `s1`. The slot at `0x18(sp)` holds the original `ra`. On the zero branch, `ra` is still that original value and `v0` is still `0x800be768`. On the return from the wrapper, `ra` is `0x80010cc4` and `v0` is whatever `__builtin_delete` left. This note covers 3 instructions, including the delay slot, and stops at the first unnamed `jal`. The hard cap is 64 instructions.

`addu` at `0x80010cc4` copies `s0` into `a0`. `jal` at `0x80010cc8` targets `0x8002fc2c` and sets `ra` to `0x80010cd0`. The delay slot at `0x80010ccc` copies `s1` into `a1`. `a0` is the object. `a1` is the second argument. `python3 tools/sdk_match.py build/disc/SLUS_004.91` does not name `0x8002fc2c`. The BIOS table in [bios.md](bios.md) does not name it. This note does not enter that body.

This block writes `a0`, `a1`, and `ra`. It reads `s0` and `s1`. It does not read `v0`, `a0`, `a1`, or the stack slots. It does not write `s0`, `s1`, `v0`, or `sp`. `s0` stays the object. `s1` stays the second argument. `v0` stays as it arrived. `ra` leaves as `0x80010cd0`. The saved original `ra` stays at `0x18(sp)`.

After the delay slot, control goes to `0x8002fc2c`. The body at `0x8002fc2c` is not traced. The words at `0x80010cd0` are not traced. Both addresses are inside the text image, `0x80010000` through `0x800c57ff`. This note does not close the gap in `components/exe/load.cpp`.

## Our code

`components/exe/call_80010cc4.cpp` copies the object and the second argument into the call arguments. It does not enter `0x8002fc2c`. That call stays marked in the source. A host check calls the block and does not change the object bytes. It does not execute the retail callee. No ledger row is added.
