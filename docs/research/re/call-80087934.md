# Block at 0x80087934

Traced fact from the USA PS-X EXE. Re-check on a disc you own with `python3 tools/entry_disasm.py build/disc/SLUS_004.91 --start 0x80087934`. The executable and the listing stay in `build/`.

The start address is `0x80087934`. It is not in `tools/sdk_names.txt`. `python3 tools/sdk_match.py` does not name it. The `jal` in [call-80087634.md](call-80087634.md) calls here and sets `ra` to `0x8008766c`. On arrival `a0` is `0x1ff` and `a1` is `0x1df`. The bytes from `0x80087934` through `0x800879c8` are the same shape as [call-8008789c.md](call-8008789c.md), with `lui` immediate `0xe400` where that note has `0xe300`. The halfwords at `0x800b75cc` and `0x800b75ce` are still 0. Both `bltz` tests are not taken, because `0x1ff` and `0x1df` are positive. Each `slt` against `-1` is true, so both results become `-1`. The hard cap is 64 instructions. This block ends at `jr ra` before the cap.

`andi` keeps the low 10 bits of `-1`, so the field is `0x3ff`. `sll` by 10 leaves `0xffc00`. `lui` writes `0xe4000000`. `jr` at `0x800879c4` returns through `ra`. The delay slot joins the fields, so `v0` is `0xe40fffff`. `ra` is `0x8008766c`. This block does not store that word.

After the delay slot, control goes to `0x8008766c`. `v0` is `0xe40fffff`. The words there are not traced. The display x and y halfwords are still not quoted. This note does not close the gap in `components/exe/load.cpp`.
